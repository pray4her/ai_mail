# Draft Reply Style Template Plan

## Goal

Add controlled 草稿回复样式 for automatically generated 草稿回复 while preserving the current plain-text behavior as a fallback.

## Decisions

- AI generation remains plain text only.
- The backend renderer owns HTML generation and inline CSS.
- Styled drafts use `multipart/alternative`: `text/plain` plus `text/html`.
- `style.enabled=false` keeps the existing plain-text-only behavior.
- The first version uses global configuration under `app.mail.auto-reply.style`.
- Template configuration is loaded from `application.yml` and environment variables only; no database tables or management UI are added.
- `MailSendService.saveDraftToFolder` keeps its current interface; the implementation applies rendering internally.
- The database `reply_content` keeps the AI-generated source text, not the rendered template output.

## Supported First-Version Components

- Plain-text fallback.
- Basic HTML email body.
- Single-column table layout.
- Header, body, and footer sections.
- Text signature.
- Ordinary links detected from body text.
- One configured CTA link button.
- Logo image from HTTPS URL with required alt text and fixed maximum width.
- Basic inline CSS generated by the system.

## Explicitly Unsupported

- External CSS.
- JavaScript.
- Forms.
- Complex animation.
- Flex/Grid layout.
- Complex responsive layouts.
- Raw webpage HTML passthrough.
- CID images.
- Image signatures.
- Arbitrary CSS editor.
- Arbitrary HTML editor.
- AI-generated structured CTA.

## Configuration Shape

```yaml
app:
  mail:
    auto-reply:
      style:
        enabled: true
        font-family: system
        font-size-px: 14
        text-color: "#1f2937"
        muted-text-color: "#6b7280"
        link-color: "#2563eb"
        background-color: "#ffffff"
        container-background-color: "#ffffff"
        line-height: 1.7
        paragraph-spacing-px: 12
        max-width-px: 640
        content-padding-px: 0
        header:
          enabled: false
          company-name: ""
        logo:
          enabled: false
          logo-url: ""
          logo-alt: ""
          logo-max-width-px: 120
        footer:
          enabled: false
          text: ""
        signature:
          enabled: false
          text: ""
        cta:
          enabled: false
          label: ""
          url: ""
          background-color: "#2563eb"
          text-color: "#ffffff"
```

## Validation Rules

- Invalid base style values fail application startup.
- Enabled optional components with missing required fields fail application startup.
- Disabled optional components may leave fields empty.
- CTA URL allows only `http`, `https`, and `mailto`.
- CTA label length is 1 to 40 characters and CTA URL length is at most 2048 characters.
- Ordinary auto-linked body URLs allow only `http`, `https`, and `mailto`.
- Logo URL allows only `https`.
- Logo alt text is required when the logo is enabled.
- Header requires either a company name or an enabled logo when the header is enabled.
- Plain-text fallback is never disabled when styled drafts are enabled.
- Numeric ranges are strict: font size 12 to 18 px, line height 1.2 to 2.0, max width 320 to 800 px, paragraph spacing 0 to 32 px, content padding 0 to 48 px, and logo max width 40 to 240 px.
- Colors must use six-digit HEX values such as `#1f2937`.
- Font family is an enum: `system`, `microsoft-yahei`, `serif`, or `monospace`.

## Rendering Rules

- Treat AI output as plain text.
- HTML-escape body text and configured text fields before rendering.
- Split body text into paragraphs by blank lines.
- Convert single newlines inside a paragraph to `<br>`.
- Generate ordinary links only from safe URL protocols.
- Do not link bare domains such as `example.com` or `www.example.com`.
- Do not rewrite URLs or add tracking parameters.
- Render ordinary links with the original URL as the link text.
- Generate CTA as a table-based link button, not a real `<button>`.
- Generate template layout using email-safe tables and inline CSS.
- Render HTML components in this order: body, CTA, text signature, footer.
- Render plain-text components in the same semantic order by appending CTA text, text signature, and footer text to the plain-text part.
- Do not include header or logo content in the plain-text part.

## Class Boundaries

- `DraftReplyStyleProperties`: typed configuration and validation for `app.mail.auto-reply.style`.
- `DraftReplyTemplateRenderer`: converts AI source text plus style configuration into final plain text and HTML.
- `DraftReplyContent`: pure data result from the renderer, with final plain-text and optional HTML parts.
- `MailSendServiceImpl`: keeps the existing public save method, calls the renderer internally, and writes either plain text or `multipart/alternative` MIME content.
- `MailAutoReplyScheduler`: continues to pass sanitized AI source text and remains unaware of styling and MIME details.

## Content Semantics

- Source text is the raw AI-generated 草稿回复正文 after existing subject-line cleanup.
- `DraftReplyContent.plainText` is the final email plain-text part and may include configured CTA, signature, and footer text.
- `DraftReplyContent.html` is the final email HTML part when styling is enabled.
- Processing records keep the AI source text in `reply_content`, not the rendered template output.

## Implementation Steps

1. Add typed configuration properties for `app.mail.auto-reply.style`.
2. Add validation for style values and enabled component requirements.
3. Add a renderer service that returns both plain text and rendered HTML.
4. Update `MailSendServiceImpl` to keep the old plain-text behavior when style is disabled.
5. Update `MailSendServiceImpl` to save styled drafts as `multipart/alternative` when style is enabled.
6. Keep `MailAutoReplyScheduler` passing sanitized AI plain text as the source content.
7. Add focused tests for configuration validation, text-to-HTML rendering, safe link handling, and MIME structure.
8. Add an optional real-IMAP smoke path that is explicitly enabled by environment variables.

## Test Scenarios

- Style disabled saves a `text/plain` draft like the current behavior.
- Style enabled saves a `multipart/alternative` draft with plain and HTML parts.
- AI text containing `<script>` renders as escaped text, not executable HTML.
- Blank lines become paragraphs and single newlines become `<br>`.
- `https://`, `http://`, and `mailto:` body links become anchors.
- `javascript:` and other unsafe protocols remain escaped text.
- Enabled CTA with a valid URL renders as a link button.
- Enabled CTA with an unsafe URL fails startup validation.
- Enabled Logo with HTTPS URL and alt renders an image.
- Enabled Logo with non-HTTPS URL or empty alt fails startup validation.
- Plain-text output includes configured CTA, text signature, and footer when enabled.
- Database reply content remains the AI source text.

## Test Strategy

- Default automated tests must not require a real IMAP server.
- Renderer tests cover escaping, paragraph conversion, safe link handling, CTA rendering, signature rendering, footer rendering, logo/header rendering, and plain-text component appends.
- Configuration tests cover valid defaults, invalid numeric ranges, invalid colors, invalid protocols, and enabled components with missing required fields.
- `MailSendServiceImpl` can be tested lightly around MIME behavior; if MIME construction becomes hard to test in place, extract a small factory later.
- A real IMAP smoke test may be added as an explicitly enabled integration check. It should save a styled draft to `AI_reply_test`, use a smoke-test subject with a timestamp, and avoid automatic cleanup so the rendered result can be inspected manually.
